# Pokémon TCG Pocket / BlackBox — consolidated investigation

**Canonical document, updated 2026-09-27.** This combines the former investigation, Windows handoff, three-environment comparison, and generic probe instructions. Raw logs, JSON captures, probe source, and APK remain as separate artifacts.

## Read this first

Pokémon TCG Pocket runs in Multiple App on the same device but still crashes in BlackBox. The first native fault and its immediate branch are understood; **why BlackBox reaches that path remains undetermined**. The boot-time `IsVspaceApp()` invocation returns true in BlackBox after reading its backing `ApplicationInfo.dataDir` and directly produces an immediate `dvsa` event, but neither value is proven to cause the SIGSEGV. PAD is secondary. The current strategy is a general Android-environment comparison, using the same diagnostic APK normally, in Multiple App, and in BlackBox.

The user-0 virtual-package `getPackageUid()` mismatch and unconditional Play Store installer name were corrected and merged into `main`. Commit `517766e` added native logical-path routing: the generic probe reads and writes the same private files through Java and native libc in BlackBox virtual users 0 and 1. The next direct-boot investigation found that BlackBox's virtual DE directory is actually under the host's CE data root, so before-unlock DE availability is **not established and structurally unlikely**. Framework path presentation remains unchanged. Nonzero virtual-user UID reporting remains unresolved. Multiple App presents a conventional logical `dataDir` while maintaining isolated storage; BlackBox still exposes its backing path. That string difference is not, by itself, a demonstrated API-contract violation or crash cause.

**Boundaries:** Do not patch Pokémon, `IsVspaceApp`, `dvsa`, `vspaceApp`, `Chs`, `Dcrs`, `Crs`, the invalid branch, or other game/security logic. Do not clear app data or change BlackBox's restored SDK-28 host baseline. Distinguish direct evidence, inference, and hypotheses; make only general BlackBox correctness changes supported by independent Android API evidence.

## Direct-boot storage gate (2026-09-27)

**Finding: the current virtual DE layout is not a demonstrated direct-boot implementation.** `BEnvironment.sVirtualRoot` is constructed from the parent of the host's ordinary `Context.getCacheDir()`, which is `/data/user/0/top.niunaijun.blackbox`. `BEnvironment.getDeDataDir(package, userId)` appends `blackbox/data/user_de/<virtual user>/<package>` *under that CE root*. `PackageManagerCompat.generateApplicationInfo` reports this physical path as `deviceProtectedDataDir`, and `IOCore` maps `/data/user_de/0/<guest>` to it. Thus Java/native agreement **after unlock** does not imply availability before the host credential is unlocked. The host manifest has no `directBootAware` component, and `BroadcastManager.onSystemStarted()` sends both `LOCKED_BOOT_COMPLETED` and `BOOT_COMPLETED` when the container starts, without gating the first on an actually locked host user. These are source facts; a secure locked-user execution failure was not measured on this device.

**Focused probe.** The direct-boot-aware generic `BootProbeReceiver` now records the broadcast action, `UserManager.isUserUnlocked()`, CE and DE paths, a DE marker write, and Java/native reads of that marker through both the Context path and logical `/data/user_de/0/<guest>` path. It also attempts Java/native reads of the existing CE marker. Results are logged before attempting to persist a JSON line in DE storage, so a future DE write failure remains visible in logcat. An ordinary device reboot was run twice without clearing data. This Pixel 7 Pro reports file-based encryption (`ro.crypto.type=file`), but `locksettings get-disabled` is `true`; both device users were `RUNNING_UNLOCKED` when tested. Every captured `LOCKED_BOOT_COMPLETED` event therefore reports `userUnlocked=true`, including stock Android. None is evidence of before-unlock DE access or expected CE denial.

The per-user DE marker contents and backing paths differ in BlackBox, while their logical DE path strings are the same. This verifies **unlocked** user isolation and path routing, independently of the known virtual-user UID reporting issue. Persistent raw receiver records are [`normal-directboot-events.txt`](android-env-probe/normal-directboot-events.txt), [`blackbox-directboot-user0-events.txt`](android-env-probe/blackbox-directboot-user0-events.txt), and [`blackbox-directboot-user1-events.txt`](android-env-probe/blackbox-directboot-user1-events.txt). The reboot logcat is [`directboot-reboot-control-logcat.txt`](android-env-probe/directboot-reboot-control-logcat.txt). The two focused unlocked-control assertions pass. The existing compatibility suite still has its one expected user-1 UID failure: **22 pass, one expected failure** across 23 checks.

**Boot delivery bug exposed and fixed.** The first reboot reached user 1's `LOCKED_BOOT_COMPLETED` receiver, then BlackBox's `BootBroadcast` thread crashed at `BroadcastManager.java:241`: its catch logger read `info.name` after a receiver query returned a `ResolveInfo` without `ActivityInfo`. This stopped delivery of the following `BOOT_COMPLETED`. A narrow, general guard now skips such results and logs their count once per action. On the second reboot, both actions reached the user-1 probe and no `BootBroadcast` fatal exception occurred; see [`directboot-broadcast-control-logcat.txt`](android-env-probe/directboot-broadcast-control-logcat.txt) and the latest user-1 receiver records. This fix does not alter guest storage, UID, Pokémon, or security logic.

**Framework-path decision.** The direct-boot gate is not satisfied. Do not yet change `ApplicationInfo.dataDir`, `deviceProtectedDataDir`, `credentialProtectedDataDir`, or Context directory answers to logical paths, and do not run Pokémon as an integration test. Such a change would present a coherent path *after unlock* while still promising a DE namespace backed by potentially unavailable CE storage before unlock. A general direct-boot design first needs a physical host DE root, a before-unlock-accessible virtual package/user registry and guest APK/native-code bootstrap path, correct ordering of locked/unlocked broadcasts, and a data-preserving migration policy for existing virtual DE files. It then needs a real locked-user test on a device with a secure credential, including expected CE failure and DE Java/native success before guest application startup. This device currently has no secure lock; setting one was not done as part of this probe. No framework-path or Pokémon change was made in this phase.

## Native logical-path routing on main (2026-09-27)

**Scope and model.** This work starts from `main` after the PackageManager UID and install-source fixes. It does not change `ApplicationInfo.dataDir`, Context directory answers, the game, PAD, target SDK, or installed app data. `IOCore.enableRedirect` remains the single producer of per-process logical-to-backing rules. The Java/libcore hooks and the new native libc hooks consume those same rules, so the conventional `/data/user/0/<guest>` and `/data/data/<guest>` paths resolve to the current virtual package/user's isolated backing directory. A new `/data/user_de/0/<guest>` rule resolves to that virtual user's DE backing directory. The mapping is longest-prefix and component-boundary aware: `<guest>` does not match `<guest>.suffix`, and a `..` suffix cannot escape a rule root. Already translated backing paths are not translated again. Native operations on dirfd-relative names use the backing directory fd opened by the same routing; absolute `*at` names are translated independently. Thread-local depth prevents hook recursion. These are general container rules, without a package-specific exception.

**Exact native hooks.** `FileSystemHook` now installs Dobby hooks for libc `open`, `open64`, `__open_2`, `openat`, `openat64`, `__openat_2`, `stat`, `lstat`, `fstatat`, `access`, `faccessat`, `realpath`, `readlink`, and `readlinkat`. It also covers `rename`, `renameat`, `unlink`, `unlinkat`, `mkdir`, `mkdirat`, `rmdir`, `opendir`, `chdir`, `getcwd`, `symlink`, and `symlinkat` so creation, relative directory operations, and symlink targets use the same model. `newfstatat` is attempted where exported; it was unavailable in this device's libc. Android's `open64` and `openat64` alias their ordinary symbols here, while `__open_2` and `__openat_2` require separate hooks. The first device build without those FORTIFY entry points still returned `EACCES` for native `open`/`openat`; adding them made both work. Hook wrappers restore the incoming `errno` before calling libc and preserve the libc result on translated output. Successful `realpath`, `readlink[at]`, and `getcwd` of redirected backing paths return logical paths; `/proc/self/fd` link targets are also presented logically when the full target fits in the caller's buffer.

**Three-environment evidence.** The same schema-7 probe APK ran normally, in a refreshed Multiple App clone, and inside BlackBox after installing the final rebuilt SDK-28 `main` APK with `adb install -r`. No data was cleared. The final raw captures are [`normal-v9.json`](android-env-probe/normal-v9.json), [`multiple-app-v9.json`](android-env-probe/multiple-app-v9.json), [`blackbox-native-v10.json`](android-env-probe/blackbox-native-v10.json), and [`blackbox-native-user1-v10.json`](android-env-probe/blackbox-native-user1-v10.json), each with a matching `-logcat.txt`. Earlier [`blackbox-native-v1.json`](android-env-probe/blackbox-native-v1.json) and [`blackbox-native-v2.json`](android-env-probe/blackbox-native-v2.json) retain the failure-stage evidence. The probe writes a distinct marker in CE and DE, reads it through Java and native libc, and tests native create/rename/unlink, symlinks, a peer guest path, a prefix-neighbor package, and `..` traversal. The independent peer package exposes its marker through its provider; BlackBox's guest cannot open the peer's logical private path directly.

The test checks filesystem isolation independently of the known virtual-user UID discrepancy. The refreshed Multiple App clone no longer sees the previously created peer clone; its same-APK v8 capture established successful two-package Binder/provider interaction, while the v9 capture tests filesystem behavior. Multiple App's `renameat` result is a limitation of that reference capture, not a correctness target for BlackBox. Its DE `realpath` had also returned `ENOENT` in the earlier capture despite successful native DE `open`/`stat`.

**Validation and limits.** `:Bcore:testDebugUnitTest :app:assembleDebug --offline` succeeds for the final source. The capture-based Python suite has 21 checks: 20 pass and one preexisting expected failure for user-1 `Process.myUid()`/`Os.getuid()` versus virtual `ApplicationInfo.uid`. The former native logical-path expected failure is now a pass. User-0 peer service/provider binding still passes under the rebuilt BlackBox host; BlackBox's main activity and both virtual-user probe launches work. These checks demonstrate logical-path routing and observed package/user separation, not a complete security boundary against arbitrary raw syscalls or direct knowledge of physical backing paths in one Linux UID. A locked-user direct-boot test remains unperformed; DE access was tested after unlock. `ApplicationInfo.dataDir` and Context paths should be reconsidered only after broader compatibility and direct-boot checks. Pokémon was not rerun or modified.

**Next experiment.** Add a locked-user direct-boot probe and a fresh two-clone Multiple App peer comparison, then evaluate whether exposing logical framework paths can be done coherently across early startup, canonicalization, and FD links. Do not infer a Pokémon crash fix from the generic filesystem improvement alone.

## Current compatibility branch (2026-09-27)

**Historical branch scope, now merged into `main`.** Branch `codex/android-compatibility` was created without resetting or stashing the existing dirty tree. That work changed general package-manager behavior and extended the independent probe. It did not alter Pokémon, game/security logic, PAD, target SDK, or app data. ### Phase 1: package identity and install source

**Confirmed bug and fix.** Before the change, `IPackageManagerProxy.GetPackageUid` replaced an installed guest package with the host package and delegated to the real PackageManager. In virtual user 0, the probe consequently saw `getPackageUid(self)=10355`, while `ApplicationInfo.uid=10023` and `Process.myUid()=10023`. The peer package had the same discrepancy (`getPackageUid(peer)=10355`, `ApplicationInfo.uid=10024`). The hook now asks `BPackageManagerService` for the installed package's user-scoped virtual UID; `PackageManagerCompat.generateApplicationInfo` uses the same calculation. A missing or uninstalled virtual package returns `-1`; host/open system packages still delegate to Android. On the branch build, user-0 self is `10023` by all three APIs, peer PM/ApplicationInfo is `10024`, `android` remains UID `1000`, and a nonexistent name yields `NameNotFoundException`. The focused `PackageUidCompatTest` was added before this behavior change and passes. The raw comparison is [`blackbox-v7.json`](android-env-probe/blackbox-v7.json) versus [`blackbox-compat-v7.json`](android-env-probe/blackbox-compat-v7.json).

**Confirmed installer bug and fix.** The prior legacy `getInstallerPackageName` hook answered `com.android.vending` for every query, including an imported diagnostic APK. Its modern `getInstallSourceInfo` instead leaked the host APK's `com.android.shell` initiating source and null installer. The branch removes the constant and stores nullable initiating, originating, and installing package names in each virtual package's settings. Existing settings read as unknown/null through a backward-compatible trailing parcel field; updates preserve the recorded fields. Both legacy and modern APIs now read the same virtual record; an imported probe with no documented virtual installer returns null legacy installer and three null modern source names. Host/open-package queries still delegate. This records **unknown**, not a fabricated installer. A future installation flow that actually knows the initiating/installer identity should populate those fields; this work does not invent that provenance retroactively. The Android 17 device accepted the framework `InstallSourceInfo` constructed for the virtual package.

**Nonzero virtual-user limit, directly observed.** Virtual user 1's probe reports `ApplicationInfo.uid=getPackageUid(self)=110023`, but `Process.myUid()=Os.getuid()=10023`; the raw Linux process remains host user 0. See [`blackbox-compat-user1-v7.json`](android-env-probe/blackbox-compat-user1-v7.json). Source tracing found `BProcessManagerService.startProcessLocked` places only the app ID in `ProcessRecord.buid`; `ProcessRecord.getClientConfig` passes that to `BActivityThread`, and `OsStub` returns its app-ID portion. A focused capture regression reproduced the inconsistency before changing behavior. A trial that passed full `buid` and returned it from `OsStub` caused Android framework calls to treat the physical user-0 process as Android user 1. The probe then failed during startup with `SecurityException: getForceInvertState asks to run as user 1 but is calling from uid u0a355; this requires android.permission.INTERACT_ACROSS_USERS_FULL`; service calls showed the same cross-user denial. Raw evidence is [`blackbox-compat-user1-fulluid-failure-logcat.txt`](android-env-probe/blackbox-compat-user1-fulluid-failure-logcat.txt). **Both trial source edits were reverted.** A coherent nonzero-user solution needs to distinguish guest-facing UID answers from framework/Binder calls that must use the host's physical user; changing `Os.getuid()` globally is not safe. The suite marks this case an expected failure, rather than claiming virtual-user consistency is solved.

### Phase 3: logical guest filesystem design gate

Multiple App exposes `/data/user/0/dev.codex.envprobe` as `ApplicationInfo.dataDir` and its clone's native `open`, `openat`, `stat`, and `realpath` reach an **isolated** marker at that logical path. BlackBox's `IOCore` Java/libcore redirection already maps conventional logical paths to its backing store for Java calls, but the v7 native probe shows direct libc calls to those same logical paths fail with `EACCES`. The source chain is specific: `IOCore.enableRedirect` adds native rules and calls `NativeCore.enableIO`; `BoxCore.enableIO` initializes `UnixFileSystemHook` (JNI/Java file methods) and `FileSystemHook`. Yet `FileSystemHook::init` only resolves and logs libc `open`/`open64` addresses. It installs no replacement, never calls `IO::redirectPath` from either wrapper, and contains no `openat`, `stat`, or `realpath` path. This explains the observed lack of direct native redirection in this codebase. A full native-routing design must cover more than those two symbols and use boundary-aware path rules; a string substitution in `ApplicationInfo` alone would be incoherent. This does **not** establish that Multiple App uses the same mechanism.

Design a coherent logical-to-backing mapping across Java Context and PackageManager paths, direct native libc I/O and canonicalization, `/proc/self/fd` presentation, CE/DE paths, and early startup. Preserve isolation between guest packages and virtual users. Do not simply substitute a conventional `ApplicationInfo.dataDir` string: until native access is routed, that string would name an inaccessible path. Before any architectural change, require the generic suite to pass under normal Android, Multiple App, and BlackBox (allowing only explicitly documented preexisting container-specific expected failures), verify isolation and existing BlackBox functionality, and explain the improvement in Android API semantics. Only after that should Pokémon be rerun as an integration test. No logical filesystem change has been made in this branch.

Android's [ApplicationInfo reference](https://developer.android.com/reference/android/content/pm/ApplicationInfo) describes `dataDir` as the assigned persistent-data directory, `deviceProtectedDataDir` as the device-protected directory, and `uid` as the assigned kernel UID. The [PackageManager reference](https://developer.android.com/reference/android/content/pm/PackageManager) defines `getPackageUid` as the UID for the package and allows a null legacy installer name. The [InstallSourceInfo reference](https://developer.android.com/reference/android/content/pm/InstallSourceInfo) defines `getInstallingPackageName()` as the installer of record, possibly null for ADB installs. The container's virtual UID is an abstraction; the *contradictory API results within that abstraction* are the concrete UID bug.

### Source-level causes and justified changes

1. [`IPackageManagerProxy.GetPackageUid`](Bcore/src/main/java/top/niunaijun/blackbox/fake/service/IPackageManagerProxy.java) calls `MethodParameterUtils.replaceFirstAppPkg(args)` and invokes the host PackageManager. The helper replaces installed guest package names with `top.niunaijun.blackbox`, so `getPackageUid("dev.codex.envprobe")` returns **10355** instead of the virtual package's **10023**. A general fix is to answer installed guest queries from the virtual package manager using the same UID it assigns in `ApplicationInfo`; preserve host queries for genuinely open/system packages. Test user IDs other than virtual user 0 and missing-package behavior before landing it. This proposal is independently justified by self-package API consistency, regardless of Pokémon.
2. [`IPackageManagerProxy.GetInstallerPackageName`](Bcore/src/main/java/top/niunaijun/blackbox/fake/service/IPackageManagerProxy.java) unconditionally returns `com.android.vending`. The generic ADB-installed/imported probe is enough to disprove that value. A general fix needs coherent virtual install-source metadata or an honest null when unknown, with corresponding behavior for `getInstallSourceInfo`; merely replacing the constant with another fixed package would repeat the bug. This is independent of Pokémon and PAD.
3. Multiple App demonstrates a possible **architecture** for exposing normal-looking guest-private paths while keeping storage isolated. BlackBox already has logical-to-backing rules in [`IOCore.enableRedirect`](Bcore/src/main/java/top/niunaijun/blackbox/core/IOCore.java), and the probe confirms those logical paths read the BlackBox marker. Returning logical paths from every relevant API is *not yet a justified one-line fix*: canonicalization, FD links, device-protected storage, native file calls, and early startup must remain consistent. The current backing `dataDir` is an assigned working directory, so no change was made solely to alter a detection result.

No BlackBox source, game binary, security logic, or host target SDK was changed in this comparison. The only code added is the standalone probe and parser. The smallest next work is a contained fix/test of the virtual `getPackageUid` answer, followed separately by an installer-source design. A direct-boot diagnostic test would resolve the device-protected storage concern. None of these observations alone establishes the cause of the Unity SIGSEGV.

### Exact bad-target producer (2026-09-26, continued)

**PAC, BTI, and address width.** This GS201/ARM64 device's `/proc/config.gz` reports `CONFIG_ARM64_VA_BITS=39`, `CONFIG_ARM64_PTR_AUTH=y`, and `CONFIG_ARM64_BTI=y`. Both an ADB shell process and a process run under the debuggable host UID reported `AT_HWCAP=0x119fff` and `AT_HWCAP2=0`: `HWCAP_PACA`, `HWCAP_PACG`, and `HWCAP2_BTI` are absent. The hardware therefore does **not** advertise userspace PAC or BTI, despite kernel support being compiled in. The exact installed `libunity.so` and `libil2cpp.so`, and `libblackbox.so` extracted from the restored original host APK (Build ID `1336437c7171e8e2b41120aac59f932fabc73c81`), contain no `.note.gnu.property` PAC/BTI feature note. On hardware without PAC, the hint-space PAC instructions act as NOPs; see [Linux kernel pointer-authentication documentation](https://www.kernel.org/doc/html/latest/arch/arm64/pointer-authentication.html) and [Arm's PAC/BTI ELF-note explanation](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/enabling-pac-and-bti-on-aarch64). **The actual instruction sequence.** In the exact installed `libil2cpp.so` (Build ID `503a9fbdd520856f620af6c55c0bd66aa579cf0b`), the following ARM64 instructions are in the executable segment; the full nearby disassembly is `branch-source-disassembly.txt`:

```asm
libil2cpp.so+0x305faf8  adr  x8, 0x305f9e0
libil2cpp.so+0x305fafc  mov  w9, #0x2359
libil2cpp.so+0x305fb00  mul  x8, x8, x9
libil2cpp.so+0x305fb04  mov  x30, x8
libil2cpp.so+0x305fb08  br   x30
```

`ADR` yields `libil2cpp_load_base + 0x305f9e0`. For the uninstrumented run, `(0x72e3828000 + 0x305f9e0) * 0x2359 = 0x000fdd76ce1bfee0`, **exactly** the first-fault PC/LR/`x8`. The equation matches all eight table rows byte-for-byte and also a ninth, new stack-probe run (`branch-equation.txt`). The precise first bad value is produced in **`x8` at `+0x305fb00`**, copied to LR/`x30` at `+0x305fb04`, and used by **`br x30` at `+0x305fb08`**. This is not `BLR x8`: a normal branch-with-link would set LR to its following instruction. It is not a `RET`/`RETAA` or a function pointer loaded from an object at the final branch. `BR` leaves LR alone, and this code explicitly makes LR equal to `x8` one instruction beforehand. [Arm's A64 branch overview](https://developer.arm.com/-/media/Files/pdf/graphics-and-multimedia/ARMv8_InstructionSetOverview.pdf) explains the distinct `BR`/`BLR`/`RET` effects.

**Why the stack would not unwind.** `libil2cpp.so+0x305f9e0` first allocates `0x20` bytes, stores old `x29/x30` at `[sp+0x10]`, and sets `x29=sp+0x10`. Two loops then each run indices `0..998`. The first stores a calculated 32-bit value at `x29-4+4*i`, writing upward approximately 4 KB and overwriting the saved frame record (`i=1..4` covers `[x29]` and `[x29+8]`). The second writes at `x29-4-4*i`, extending below the current SP. The value is `low32((libil2cpp_base+0x305f9e0)*i + (x29-4))`. The tombstone words at `[x29]` and `[x29+8]` match that formula in **all eight** earlier runs (`stack-pattern-eight-runs.txt`). Thus a conventional frame-pointer walk cannot recover the caller; the apparent random words are produced by this function itself, rather than evidence of an unidentified overwrite elsewhere.

A new, temporary first-signal probe captured registers plus 16 KB from the original `UnityMain` SP **before** forwarding to Unity's handler (`stack-probe/first-stack.bin`, with matching `tombstone_04.txt`). The first loop's predicted words match the snapshot at indices 0, 1, 2, 3, 4, 100, 997, and 998, including both saved-frame slots; the pattern ends at `sp+0xfa4` (`stack-formula.txt`). Above that, 27 executable-looking stack words in the 16 KB snapshot map to ART/JIT/libc, none to `libunity.so` or `libil2cpp.so`. The eight older 98-word tombstone stack windows likewise contain no executable address and no valid `x29` chain (`stack-reconstruction.txt`). There is therefore **no defensible recurring game-library return-address candidate** to report from those stacks. The direct disassembly and arithmetic, rather than a guessed stack return, identify the branch source.
